# Banking integration: repository findings and design proposal

Research date: 2026-09-20. Status: **Phase 2 research approved; sandbox implementation added, hosted flow unverified**. See [banking integration setup](banking-integration.md) for the current implementation and verification status. Public provider terms and bank coverage can change; confirm the commercial terms and live institution list before production deployment.

## Phase 1: existing application

- This repository is named Spendime in code and documentation; the requested Equilibria name needs a separate branding decision. It is a Node 22 TypeScript Express 5 API with a React 19, React Router 7, TanStack Query, Tailwind and Vite PWA. PostgreSQL 16 is accessed through `pg`, with handwritten SQL rather than an ORM.
- Authentication is email/password with Argon2id. An opaque random token is hashed in `auth_sessions` and sent in a host-only, HttpOnly, SameSite=Lax cookie. `requireAuthentication` resolves the active user. `withUserTransaction` sets transaction-local `app.current_user_id`, and RLS plus composite same-user foreign keys protect financial tables. The runtime role is checked at startup. `requireSameOrigin` currently protects register, login, and logout, but is not applied to financial mutations; banking mutations must receive explicit origin/CSRF protection.
- `accounts` hold currency and opening balance. The `account_balances` view calculates opening balance plus non-voided transaction effects. Bank-reported balances are not represented. `transactions` have kind, one amount/currency, source/destination account IDs, optional category, merchant, dates, and void metadata. Amounts are positive decimal strings at the API boundary. Currency must match referenced accounts. Same-currency internal transfers are one `transfer` row. Cross-currency transfers are not supported.
- Categories are per user, with seeded system categories and optional custom categories. Dashboard SQL groups cash flow and spending by currency, excludes transfers from income/expense, and uses `daily_financial_impact` for utility costs. There is no FX-rate model, budget model, bank connection, AI categorization, or automatic recurring job. Recurring rules are templates only.
- Express routers use Zod, `inUserTransaction`, repositories and services. The frontend has a responsive `AppShell`, account and transaction pages, reusable UI components, and query invalidation. The API has no-store cache headers, and the PWA does not cache `/api/*`.
- Deployment is a single Express container plus PostgreSQL on Docker Compose, designed for Raspberry Pi ARM64. Numbered SQL files initialize only empty volumes; existing databases require manual additive migrations. The app container has a 256 MB memory limit. There is no background worker or queue. Vitest, Supertest and React Testing Library cover PostgreSQL integration and UI behavior; database tests need a configured PostgreSQL instance. There is no lint script.

Relevant integration points: `src/server/app.ts`, `src/server/config.ts`, `src/server/db/transactions.ts`, `src/server/domains/{accounts,categories,transactions,dashboard}`, `src/client/app/App.tsx`, `src/client/components/AppShell.tsx`, `src/client/api`, `database/init`, `docker-compose.yml`, and `tests`.

### Bulgaria coverage evidence and limits

Enable Banking's [Bulgaria market guide](https://enablebanking.com/docs/markets/bg/) describes authorization at DSK, UBB, UniCredit Bulbank and Postbank. Its provider [changelog](https://enablebanking.com/blog/2025/08/22/changelog-august-2025) lists DSK and Revolut including BG; a [2026 update](https://enablebanking.com/blog/2026/05/14/enable-banking-changelog-april-2026) lists UBB; and an [August 2026 update](https://enablebanking.com/blog/2026/09/09/changelog-august-2026) lists Postbank. These establish documented integrations or bank flow knowledge, not an uptime or eligibility guarantee. UniCredit is described in the market guide, but its current production AIS status was not independently established. Before launch, query `GET /aspsps?country=BG&service=AIS` with provider access and test each target bank and account type. Do not hardcode a five-bank promise.

### Provider behavior that shapes the adapter

- Enable Banking [FAQ](https://enablebanking.com/docs/faq/) says background retrieval can be limited to four calls/day at many banks, with a recommended six-hour pause after a bank 429. Consent validity comes from each bank, often about 180 days, and can end early. The provider handles bank token refresh. Schedule within per-bank limits and show renewal when needed.
- Initial history is bank dependent. The [FAQ](https://enablebanking.com/docs/faq/) says older history may be obtainable only shortly after authorization; fetch the longest available history immediately, then use overlapping recent windows. Follow `continuation_key` until absent, even after empty pages.
- Enable Banking's [transaction schema](https://enablebanking.com/docs/api/reference/) marks `entry_reference` as an optional stable identifier **scoped to an account**, while `transaction_id` may change between fetches and cannot uniquely identify a transaction. Account IDs change on renewal; use `identification_hash` to relink accounts only within the same Equilibria user. Store no full IBAN unless a justified workflow requires it.
- The [webhook documentation](https://enablebanking.com/docs/api/webhooks/) documents payment-status webhooks. No transaction-change webhook was verified, so the design uses controlled polling. A later provider may expose one behind the abstraction.
- [Session deletion](https://enablebanking.com/docs/api/reference/) closes the bank consent where possible. Deletion of locally retained transactions is a separate user-facing choice and retention-policy decision.

## Proposed architecture after approval

1. Add a provider-neutral `BankingProvider` interface for discovery, begin authorization, complete callback, list accounts, fetch balances and paginated transactions, inspect consent, and disconnect. An Enable Banking adapter would be the first implementation **only if approved**. The frontend sees provider-neutral DTOs and no provider credentials.
2. Add user-owned bank connections and connection attempts. Bind a short-lived, random, single-use state to the authenticated user, provider, selected institution and callback origin; validate it before exchanging a code. Require an active same-user session at callback, handle expired login safely, and reject replay. Banking writes need same-origin or CSRF-token enforcement in addition to SameSite cookies. Restrict redirect URLs to configured HTTPS origins, except local sandbox testing.
3. Add a user-owned connected-account link to an existing `accounts` row rather than duplicating ledger accounts. Store provider account identity hashes, current session-specific account IDs, consent expiry, sync cursor/watermark, bank-reported balance with as-of time, and sync status. Use RLS, same-user composite foreign keys, and include new tables in startup RLS verification and runtime role grants. Keep provider private keys in server-side secret configuration, encrypted at rest if stored outside a secret manager; never send them or bearer JWTs to the browser.
4. Stage minimal normalized bank transaction facts with provider ID or account-scoped fingerprint, status, timestamps, amount, currency and redacted descriptive fields. A unique database constraint makes re-import idempotent. Store pending items outside the posted ledger; replace or link them when booked. Use `entry_reference` when present; otherwise a versioned account-scoped fingerprint plus bounded fuzzy matching and a review queue. Never rely on Enable Banking `transaction_id` as the dedupe key. Handle refunds and reversals with explicit linkage and regression-tested dashboard semantics.
5. Post only reconciled booked movements into `transactions`. Manual entries remain untouched. For a new bank account, calibrate `opening_balance` only when the bank's booked balance and imported history have a compatible snapshot; otherwise show the reported balance separately and flag the ledger as unreconciled. Linking an existing account requires a manual matching review before overlapping bank entries post, preventing double counting.
6. Match two sides of an own-account transfer only with strong account-identity and amount/date evidence. Same-currency matched legs become one existing `transfer` entry. Cross-currency matched legs need two linked `adjustment` entries or an explicit new FX transfer model so each account keeps its original currency while analytics exclude both legs. Refunds require a ledger kind or linkage that reduces net spending without inflating ordinary income. These are proposed **financial schema/calculation changes**, to review before migration.
7. Use a database-backed sync lease and due-time table, run by one low-concurrency worker process/container in Compose. Commit account/page checkpoints and ledger posts atomically; overlap incremental windows, retry with capped backoff, honor 429/reset limits, and resume after interruption. Trigger initial import immediately after callback. A manual sync request respects the same quota. Provider failures do not erase prior data.
8. Categorize in order: user rules, confirmed per-user merchant preference, deterministic rules, optional Gemini, then uncategorized. Preserve a user-edited category with an override flag. Cache only within the user's scope. Send only trimmed merchant/description, direction, amount/currency if needed, and active category IDs/names to AI. Validate structured output with Zod and recheck category ownership/kind. Never send account identifiers, names, IBANs, tokens, or raw provider payloads. Fail open to uncategorized.
9. Extend existing `AppShell`, accounts/transactions UI and TanStack queries with bank search, consent redirect, connected accounts, balances, sync/expiry status, renewal, disconnect, and safe error messages. Distinguish bank-reported balance from calculated ledger balance. The provider's hosted/bank authorization page collects any bank credentials.

## Gemini feasibility and privacy gate

The official [JavaScript/TypeScript Google GenAI SDK](https://ai.google.dev/gemini-api/docs/libraries) is `@google/genai`; [structured output](https://ai.google.dev/gemini-api/docs/structured-output) supports JSON schema but still requires server validation. The [model list](https://ai.google.dev/gemini-api/docs/models) currently lists `gemini-2.5-flash-lite`, a suitable cost-first starting point, and the [pricing page](https://ai.google.dev/gemini-api/docs/pricing) lists standard paid text input at **$0.10/million tokens** and output at **$0.40/million tokens**, with a free tier. Quotas vary by project and must be checked in [AI Studio](https://ai.google.dev/gemini-api/docs/rate-limits); no fixed free request quota is assumed.

For a user-facing EEA app, Google's [additional terms](https://ai.google.dev/gemini-api/terms) say only Paid Services may be used. An API request is a Paid Service only through a Cloud project with active billing. Google's general unpaid-service terms allow product improvement and human review; the terms state an EEA data-use exception, but this does not remove the need to verify the account/project configuration, privacy notice, lawful basis, data-processing terms and transfers. Default real-data AI processing to **off** until those prerequisites are completed; deterministic categorization remains available. Recheck model ID, price and terms at implementation time.

## Decisions and prerequisites before Phase 3

1. Approve or change the conditional choice of Enable Banking. Obtain its quote, written acceptance of this multi-user consumer finance use case, Bulgarian entity eligibility, production terms and KYB requirements. Confirm live AIS coverage and account types for DSK, UBB, UniCredit Bulbank, Postbank and Revolut. A sandbox account is not production authorization.
2. Approve the data policy: historical import window; disconnect behavior (keep ledger history versus delete linked records); retained bank metadata; and manual-account linking/reconciliation UX. Resolve whether Equilibria is a rebrand of Spendime before changing visible labels.
3. Approve financial model changes for refunds and cross-currency own transfers. The current schema cannot represent both correctly without a small additive migration and analytics regressions.
4. For public deployment: obtain provider contract and AISP model confirmation, publish terms/privacy and data-protection contact, complete GDPR controller/processor and retention review, set up HTTPS and secret management, monitoring/backups and incident process. This design is not a legal-compliance claim.
5. Enable Gemini only after active-billing, DPA/privacy review and a user disclosure/choice have been established. AI is optional and must not delay bank sync.
